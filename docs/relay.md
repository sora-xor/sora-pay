# Private Sora Pay merchant relay

The static storefront never stores shipping details on IPFS or on-chain. This Node 26 service saves encrypted private orders before exposing payment requests. It never accepts wallet signing keys. The concrete SORA reader scans `liquidityProxy.XorlessTransfer` events in finalized successful extrinsics, including public `sp_…` references. An `assets.transfer` without that reference is not automatically matched; a volunteer must reconcile such a direct/unreferenced payment manually before refunding it. The scanner does not trust browser transaction hints.

Use the [disabled staging workflow](staging.md) to package a pinned, isolated Node 26.9.0 runtime. The runner never uses the shared MOF Homebrew Node 24. The supplied launchd template is deliberately disabled and never starts a service on its own.

## Configuration and startup

1. Build with `yarn build` using Node 26. For Polkaswap, copy `deploy/merchant.polkaswap.json.example` to a private deployment directory. It contains the fixed XOR product/shipping catalog and internal launch conversion audit. Confirm native-chain genesis/denomination and the first finalized block to scan before enabling it. The minimal `merchant.disabled.json.example` is also available for configuring another deployment. The real group wallet and support contacts are prefilled. Sample defaults are **disabled**. Product weight is 120 g per bag plus 80 g per parcel; weigh a packed example before enabling shipping. On-demand mode has no stock cap; 30 minutes is the payment quote expiry, not a stock promise. The optional `stocked` mode requires a stock count and reserves it atomically.
2. The Polkaswap public operator is **Community Volunteers**, with public support only through [@sora_xor](https://t.me/sora_xor). Both shipped Polkaswap templates omit `supportEmail`. Review dispatch/customs/cancellation/privacy policies with the operator. An enabled merchant must configure at least one public contact: optional `supportEmail` must be a valid plain email address; optional `supportTelegram` must be a bare handle without `@` or a URL, starting with an ASCII letter and containing 5–32 ASCII letters, digits or underscores. Every supplied contact is validated, even when another valid contact exists. All merchant identity and policy fields remain required. These public support fields do not configure the private notification destination. A customer's optional `@telegram_handle` is private contact information; volunteers contact them manually for acknowledgment and tracking. The bot automatically sends only to the configured private volunteer destination. Operator should acknowledge paid orders and communicate tracking/refund status; receipts also expose status privately.
3. Generate independent encryption and operator tokens using a secure random generator. Put secrets in an owner-only `relay.env` outside source control. Use one Telegram or SMTP transport; startup rejects an enabled store with no transport. Never place these secrets or a wallet key into frontend configuration. Restrict the private directory to mode 0700, database/backups/env to 0600. Keep the encryption key separately from the database and separate from backup keys.
4. Set exact HTTPS `allowedOrigins` (Polkaswap plus individually approved IPFS origins when needed); no wildcard origins. Bind the service to loopback, provide TLS through approved nginx, disable HTTP body/header/access logging, apply per-client rate limits before proxying, and restrict `/v1/operator/` to the operator VPN. The application also requires a bearer operator token. Once the bundled nginx configuration is installed, explicitly set `SORA_PAY_TRUST_LOOPBACK_PROXY=1`: nginx must **overwrite** `X-Sora-Pay-Client-IP` with its own `$remote_addr` on every route, never pass a caller-supplied header through. The relay trusts that single validated IP only from a loopback socket, giving each customer a separate 240-request/minute application bucket. Default mode ignores forwarding headers and limits the direct socket address. Missing, duplicate/list, or malformed headers from the opted-in loopback proxy fail closed. Keep the listener on loopback and do not enable this option behind an untrusted local forwarder. A direct loopback health probe in proxy-trust mode must supply `X-Sora-Pay-Client-IP: 127.0.0.1`; this header must not be exposed as an accepted cross-origin browser header.
5. Verify MOF CPU/memory/disk capacity and private storage permissions before installing the separate launchd service. Before the public pilot or a release import, apply the [MOF storage admission budget and response thresholds](mof-capacity-policy.md); readiness alone does not enforce them. This service may not disrupt the existing SORA RPC, IPFS gateway, nginx blocks, or unrelated processes. Deployment examples are templates requiring real paths/service identity. No infrastructure credentials are embedded. Never use a prohibited infrastructure provider.
6. Start with `node --env-file=/private/relay.env dist/relay/cli.js serve`. The relay stays unready during catch-up, RPC failure, denomination/precision mismatch, or incomplete setup. `/healthz` reports readiness; alert on non-ready status and old undelivered jobs. The service has no inbound webhook that can assert payment.

The approved MOF primary RPC retains only 256 blocks of historical state. The disabled Polkaswap configuration explicitly uses the existing approved OVH archive at `wss://mof2.sora.org` through `chain.archiveRpcUrl`, while `chain.rpcUrl` remains `wss://ws.mof.sora.org`. Existing Polkaswap archive documentation and its MOF2 recovery runbook identify that archive and provider. This historical-read role does not switch production primary traffic. Generic merchant templates and the reusable relay still have no default archival endpoint: another deployment must explicitly configure an approved `wss://` source exposing the original chain's historical event state.

The reader first obtains the primary RPC's finalized height and canonical block hash; an archive is used only for unavailable historical state, and its genesis, block hash at that height, and returned header hash must match. An archive cannot extend the primary's finalized height. A September 25, 2026 read-only probe of the actual relay reader verified block **27,771,081**, 1,024 blocks behind primary finalized head **27,772,105**, with hash `0x91cc0f08aa6a26571fde31bffb80eb7a4ef395d822505f9708c3c395fb59422f`. Primary state was discarded; the archive matched mainnet genesis and the primary's canonical hash, and historical events decoded successfully. No payment or refund was submitted, and this probe did not match a store payment reference.

Missing historical state without a usable archive raises `archive_required`, preserves the durable scan cursor, and disables new checkout. Do not advance the cursor manually to regain readiness: doing so can lose payments. For a brand-new deployment, set `startBlock` to a recent verified finalized block immediately before accepting orders; the dated sample value is a reference, not a live deployment value. Existing databases always resume their saved cursor. Rehearse durable restart recovery across the primary's pruning horizon against the configured archive before enabling checkout; a successful historical read is not a paid-order/refund rehearsal.

The Polkaswap merchant uses `pricing.kind: exact-xor`, `pricing.mode: launch-fixed`, and `product.priceXor: "1.759225"`. Each shipping band also contains a fixed `priceXor`. These amounts stay unchanged until the operator explicitly publishes a new price version. The public catalog exposes only `{kind:"exact-xor",version}` pricing metadata and XOR product/shipping amounts; it excludes internal conversion fields, original carrier JPY amounts, and the MUFG audit snapshot. The storefront displays and accepts XOR only.

For internal audit, the September 25 launch amount was calculated once as `ceil(1500 / 158.78 / 5.37 * 1e6) / 1e6 = 1.759225 XOR`. The private deployment config retains the source, date, rate, and original JPY reference. Shipping bands were converted once with that same snapshot, rounding each band upward to six places. These historical inputs are not live prices. The Polkaswap config has no MUFG runtime provider, and changes to future fiat or XOR market rates cannot reprice its product or shipping.

Japan Post availability still refreshes daily. For an exact-XOR merchant, the refresher intersects current supported destination/weight bands with the frozen launch band IDs and retains their exact XOR prices even if carrier charges change. A temporarily suspended band can return at the same frozen amount. New carrier bands with no published XOR amount stay inquiry-only until explicitly configured. `blockedCountries` adds only explicit known holds; there is no mandatory operator country allowlist. Volunteers review legality and carrier availability before dispatch, with a refund under the order’s saved policy if fulfillment is impossible. A provider failure pauses new checkout while saved orders remain recoverable.

To reprice, edit the fixed product/shipping XOR strings and advance `pricing.version`, then restart the relay with the new catalog. Existing saved orders retain their original amounts and audit snapshots. Native XOR codec amounts multiply only by `10^asset-decimals`; denomination remains a consistency guard.

Other merchants may use the reusable `jpy-fixed-usd` policy and optional daily MUFG provider. That capability is separate from Polkaswap's fixed XOR catalog. Its exact integer conversion and daily/launch-fixed choices remain available without changing this store's policy.

## Public API

All responses have `Cache-Control: no-store`. JSON request limit: 16 KiB. No query parameters. Bearer secrets and private customer fields must never enter URLs, analytics, error telemetry, public messages or blockchain comments.

| Route | Request and behavior |
| --- | --- |
| `GET /v1/catalog` | Safe merchant, pricing, product, shipping and chain fields. Exact-XOR pricing contains only `{kind:"exact-xor",version}`; no internal fiat audit fields are public. Disabled unconfigured stores return `{enabled:false,version}`. Enabled but currently unready stores return catalog with `enabled:false`. |
| `POST /v1/orders` | `{productId,quantity,shippingRateId,payer,address:{name,line1,line2?,city,region?,postalCode?,country},contact:{type:'email'\|'telegram',value},idempotencyKey}`. Random UUIDv4/32-byte key must be persisted locally before POST; it is a private capability. Validates server catalog, quantity weight, country and payer. Returns `{orderId,recoveryToken,paymentRequest,status,notificationStatus,paymentPending}`. |
| `POST /v1/orders/recover-create` | `{idempotencyKey}` restores a lost create response without retaining or replaying shipping details in the browser. Returns no PII. Same-body create retry is idempotent; a changed body under the same key is rejected. |
| `GET /v1/orders/:id` | `Authorization: Bearer <recoveryToken>` returns private status, receipt, tracking/refund details; no address/contact. |
| `POST /v1/orders/:id/payment-attempt` | Same auth, `{}` body. Atomic one-at-a-time signing lease, returns `attemptToken`. Another tab cannot acquire a second lease. |
| `POST /v1/orders/:id/payment-attempt/cancel` | Same auth, `{attemptToken}`. Release only after explicit wallet rejection before submission; never invoke after an uncertain broadcast. |
| `POST /v1/orders/:id/transaction` | Same auth, `{transactionHash}`. Hint only; does not set paid status. |

Address `name`, `line1`, `city` and two-letter uppercase `country` remain required. `postalCode` is optional: an omitted, empty or spaces-only value is stored as `""`, so checkout can accept addresses without a postal code. A supplied postal code must be a string of at most 200 characters without control characters; `null` and other value types are rejected. All supplied address fields are trimmed and retain the same length/control-character validation. Equivalent omitted/empty postal values produce the same idempotent order. Volunteers still review delivery completeness and destination requirements before shipping.

The front end pins chain/native asset/group wallet and separately validates a quote before opening a wallet prompt. Persist the recovery capability in session storage, permit downloading a receipt, and use a URL fragment only if a recovery link is needed. Never attach recovery data to query strings. Payment references are random and public; no customer data belongs in the transfer comment.

## Volunteer operations

Use a trusted operator client or CLI that passes `Authorization` from the private environment; do not put tokens in shell arguments/history. Requests below require the operator token and VPN access. The shared token authorizes the trusted volunteer team; `owner` is an operational assignment identifier, not a separate authenticated security principal.

- `GET /v1/operator/orders` returns up to 500 private orders, prioritizing outstanding paid/review/refund work oldest first with address/contact, ownership, received/refunded exact amounts and receipt evidence. No public admin page is exposed.
- `POST /v1/operator/orders/:id/claim` with `{owner}` assigns once. Another owner gets conflict.
- `POST /v1/operator/orders/:id/approve` with `{owner}` approves a late exact payment after volunteer review and stock availability, when applicable. Wrong/extra amounts require reconciliation/refund, never automatic shipment.
- `POST /v1/operator/orders/:id/ship` with `{owner,tracking,shippingReviewed:true}` requires paid, assigned state and a fresh legality/carrier review. It queues a private volunteer status notification; the volunteer sends tracking to the customer's contact. Repeated shipments are rejected.
- `GET /v1/operator/orders/:id` retrieves a specific private order, including older completed orders outside the queue limit.
- `GET /v1/operator/orders/:id/evidence` returns encrypted-at-rest finalized incoming/outgoing transfer evidence for reconciliation. A mismatched incoming amount never appears as a valid original-quote customer receipt.
- `POST /v1/operator/orders/:id/refund` with `{owner}` reserves the outstanding refund, verified original payer and a fresh public reference. A net-policy draft has no signable `amountCodec` until the relay obtains a trusted fee quote. Repeating the request preserves the obligation. Before signing, acquire `POST /v1/operator/orders/:id/refund-attempt` with `{owner}` and persist its `attemptToken`; the relay rechecks the fee before granting the lease. Another attempt is rejected while the lease is unresolved. Report a broadcast with `refund-transaction` using `{owner,attemptToken,transactionHash}`. Use `refund-cancel` with `{owner,attemptToken}` only after explicit wallet rejection before broadcast; uncertain or submitted attempts stay locked for reconciliation. A volunteer signs only the quoted native-XOR `liquidityProxy.xorlessTransfer`, from the group wallet, for the exact net `amountCodec` and public reference. No API can simply mark a refund successful. See the accounting rules below.

The Polkaswap tea configuration sets `reviewEveryPaidOrder:true`, so every paid order needs a volunteer food/import/carrier check and the `approve` operation before shipment. Payment mismatch, expiry, additional payment, or unavailable stock enters `shipping_review` instead of enabling shipment. Multiple distinct finalized transfers with the same reference accumulate the amount owed; replaying the same event is ignored. Payment acceptance and notification insertion are one SQLite transaction. Notifications are at least once: network ambiguity may duplicate a message, so volunteers use the stable order ID and private assignment queue, not the number of messages, to decide fulfillment. Delivery failures persist with bounded exponential retry. Atomic 60-second outbox leases prevent concurrent workers from sending one job together; only the current lease owner can acknowledge it. External delivery remains at least once after a crash or uncertain remote acknowledgment. Do not accept new payments on an unready service. A relay restart rescans from the durable next-block cursor and can recover a transfer even if its browser closed without sending a hash.

## Refund accounting

`refundPolicy` is an explicit versioned setting: `{ "version": 1, "mode": "full" }` returns the full outstanding XOR and the store pays the outbound fee; `{ "version": 2, "mode": "net-network-fee" }` deducts the verified outbound SORA fee, capped at the quote. Both Polkaswap templates select version 2 for newly created orders. A missing setting defaults to version 1. Orders snapshot the policy when created, and missing historical snapshots always mean version 1. Changing merchant configuration never changes a saved order or an existing pending refund. Do not rewrite historical terms as part of a deployment.

The original payment fee never enters `receivedCodec` and is not deducted again. Refunds expose `grossAmountCodec`, a quoted net `amountCodec`, and `feeQuote` containing exact fee, finalized quote block and expiry. The quote is for one direct native-XOR transfer with the public reference, zero tip and no batch or proxy fee allocation. The relay serializes a dummy-signed envelope solely to query the finalized RPC fee; no spending key is held or transaction submitted. Envelope size, nonce or runtime changes can alter the eventual fee. A changed quote is reviewed before signing; an acquired or uncertain signing lease freezes it.

Only the trusted finalized reader can supply `receipt.evidence.networkFee`. For the current runtime it corroborates one same-extrinsic `xorFee.FeeWithdrawn` with `transactionPayment.TransactionFeePaid`, checks the actual native fee payer and zero tip, and does not sum these two reports of the same fee. Nested, missing or ambiguous fee evidence is not charged to the customer. Generic receipt matching verifies the transfer; fee authority comes from the trusted reader, never an operator or browser assertion.

After the exact outgoing transfer finalizes, `refundedCodec` increases only by XOR actually returned. `refundFeesCodec` increases by the smaller of the verified actual fee and quoted fee. The store absorbs a higher actual fee. A lower actual fee leaves `feeCorrectionCodec` on that transfer and `refundFeeCorrectionCodec` on the order; it remains owed and is returned first as a separate `feeExempt` transfer whose network fee the store pays. Missing authoritative fee evidence causes a zero deduction and the entire quoted fee becomes a fee-exempt correction; the observed transfer is retained and never blindly repeated. A later additional customer payment is handled separately, after that correction. The `refund` object always describes the latest transfer, not a lifetime aggregate.

An order is fully refunded only when received XOR minus XOR returned, verified deducted fees and fulfilled purchases is zero. Insufficient gross funds for a positive net transfer leave a reviewable obligation; never create a zero-value transfer, erase the liability or mark it refunded. Keep enough XOR for existing liabilities, legacy full refunds, fee-estimate differences and fee-exempt corrections. The customer pays no extra fee for correcting the store’s estimate. Refunds have no fixed processing deadline; volunteers provide updates through the chosen contact method.

## Retention and backup recovery

The service encrypts PII with AES-256-GCM using per-record random nonces and record ID authenticated data. Address/contact are redacted after 30 days following shipment/refund by default and 24 hours after an unpaid quote expires. The original payment address, exact amounts, receipts and event identities remain for payment reconciliation. A late payment after address redaction needs the customer to contact support privately. Backups and private notification inboxes contain copies: configure matching retention in the backup destination, Telegram group and email inbox. Where legal accounting retention requires longer storage, adopt an explicit operator retention policy and restricted storage rather than silently retaining addresses forever.

Create an encrypted backup with `node --env-file=/private/relay.env dist/relay/cli.js backup`, using a unique `SORA_PAY_BACKUP_PATH` and a separate `SORA_PAY_BACKUP_KEY`. SQLite's backup API takes a consistent snapshot; the complete result is encrypted. The temporary snapshot directory is private and removed. Existing backup destinations are never overwritten. Copy encrypted backups only to an explicitly approved private destination; never IPFS or public repositories.

The current source loads only local backup dependencies for `restore`, and loads RPC, HTTP, catalog and notification modules only for `serve`. Operator wrappers should give restore and database verification separate bounded timeouts and retain safe phase/duration records. Never log subprocess commands, environment values or raw output from a failed private restore. A verification timeout leaves the encrypted archive unverified; it must not replace the last verified backup or trigger retention pruning.

For recovery, stop the exact relay launchd service, preserve its current database/WAL, and use the `restore` command to a **new** database path. Supply the original database encryption key and separate backup key; an incorrect database key fails on startup. The database pins its original chain genesis and group wallet; it refuses startup under a different merchant identity. Point the private env at the restored path, start one relay instance, let it rescan finalized blocks from its saved cursor, inspect order/outbox counts, and rehearse a recovered receipt lookup. Never run two notification workers against the same database. Backup restore may resend previously delivered messages; use order IDs and queue assignments to prevent duplicate shipments. Rehearse restore before accepting real payments.

No live deployment, purchase, notification or refund is performed by the test suite. Launch needs an internal end-to-end paid/refunded rehearsal, current shipping/legal checks, a completed private transport and the existing MOF/Bunny deployment runbook.

## Local customer checkout rehearsal

`deploy/rehearsal-proxy.mjs` provides a customer-only browser route over a **manually established SSH forward**. It runs only when explicitly invoked and loads no relay environment, operator token, wallet key or SSH credential. Build first with Node 26 and the locked Yarn setup from the README. The command without flags prints usage and exits.

Before any enabled rehearsal, block public customer ingress at the approved nginx host and verify that block externally. A null frontend `relayUrl` and CORS do not prevent direct API access. Keep the published frontend configuration unchanged. Enable the private merchant only after notification credentials, backup bindings and the reviewed start block are ready; this local proxy neither changes nor bypasses those launch gates.

For the approved MOF deployment, open a separate terminal and establish the SSH forward using the existing trusted host key and operator authentication. Do not put credentials in the command, disable host-key checks, or expose the forward on other interfaces:

```sh
ssh -NT -o ExitOnForwardFailure=yes -o StrictHostKeyChecking=yes \
  -L 127.0.0.1:39850:127.0.0.1:39848 administrator@mof.sora.org
```

Then run the local proxy from this repository:

```sh
node deploy/rehearsal-proxy.mjs \
  --listen-port 39849 \
  --upstream http://127.0.0.1:39850 \
  --frontend-origin http://127.0.0.1:41829
```

All three flags are mandatory. Only literal `http://127.0.0.1:<port>` origins are accepted, with distinct non-default ports; credentials, paths, queries, host aliases and non-loopback addresses are rejected. The browser must use **`http://127.0.0.1:41829`**, not `localhost`. The proxy binds only **127.0.0.1:39849** and requires that exact Host, the configured Origin and a loopback socket peer on every browser request. It does not accept missing or `null` origins. No environment variable changes its endpoints.

In the Polkaswap checkout, use its explicit development-only rehearsal mode:

```sh
PS_STORE_REHEARSAL_RELAY_URL=http://127.0.0.1:39849 \
  yarn vite --mode store-rehearsal
```

The Vite rehearsal server fixes its host/port to `127.0.0.1:41829` and overrides the served development `/community-store.json`. Because normal development selects the testnet environment, this explicit rehearsal mode also answers `/env.dev.json` with the **byte-identical contents of `public/env.json`**. It first requires production network type, the exact SORA mainnet genesis, primary `wss://ws.mof.sora.org`, and node addresses limited to the existing approved `ws.mof.sora.org`/`mof2.sora.org` pair. It accepts the bare environment path or its exact current `?v=` build-version query; other queries fail instead of falling through to testnet. Both overrides require the exact local Host, allow only GET/HEAD, and use no-store responses. No public configuration/environment file or app development flag is changed; ordinary development and normal builds retain their existing behavior.

Rehearsal mode limits Vite dependency discovery to `index.html` so archived HTML snapshots are not scanned as app entrypoints. Visit `http://127.0.0.1:41829/#/store`. This is a desktop loopback setup; a browser on a separate phone cannot use this address. Actual supported wallet/mobile signing remains a separate rehearsal requirement.

The proxy allows only `GET /v1/catalog`, `POST /v1/orders`, `POST /v1/orders/recover-create`, `GET /v1/orders/:uuid`, and customer `transaction`, `payment-attempt` and `payment-attempt/cancel` POST routes. It denies operator/health routes, other methods, query strings, arbitrary URLs, encoded path variants, CONNECT and WebSocket upgrades. Preflight permits only the selected route's method plus Content-Type and Authorization. Recovery authorization is forwarded only for customer order routes and must be the existing 64-hex recovery capability; never enter an operator token in the frontend.

Upstream requests go solely to the fixed SSH forward, with Origin `https://polkaswap.io` and overwritten `X-Sora-Pay-Client-IP: 127.0.0.1` for the approved relay's proxy-trust mode. Incoming cookies, forwarding headers and arbitrary headers are discarded. Upstream cookies, redirects and CORS headers are never passed through. Responses use the exact local browser origin and `Cache-Control: no-store`. There are no request URL/header/body logs, retries or persisted proxy records. POST JSON is limited to 16 KiB; each body/upstream wait has a 15-second deadline and upstream JSON is capped at 1 MiB.

Stopping the proxy with Ctrl-C closes its listener and drains for at most five seconds; stop the separately launched SSH forward as well. A timeout or browser closure may occur after an order or payment attempt reached the relay: use the existing saved idempotency key/receipt recovery and payment-status flow, never assume failure authorizes another transfer. Keep the public ingress block until the internal purchase/notification/fulfillment/refund rehearsal and launch review pass. Operator access remains a separate authenticated private workflow and is never available through this customer proxy.
