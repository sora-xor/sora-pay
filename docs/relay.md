# Private Sora Pay merchant relay

The static storefront never stores shipping details on IPFS or on-chain. This Node 26 service saves encrypted private orders before exposing payment requests. It never accepts wallet signing keys. The concrete SORA reader scans `liquidityProxy.XorlessTransfer` events in finalized successful extrinsics, including public `sp_…` references. An `assets.transfer` without that reference is not automatically matched. Unreferenced incoming payments still require separate investigation; the protected reconciliation route below covers an already-issued pending refund only. The scanner does not trust browser transaction hints.

Use the [disabled staging workflow](staging.md) to package the pinned, isolated Node runtime and an explicitly supplied merchant configuration. The inactive service template never starts a service on its own. Catalogs, destination handling, capacity decisions and deployment records are maintained by each merchant outside this toolkit.

## Configuration and startup

1. Build with `yarn build` using Node 26. Copy `deploy/merchant.disabled.json.example` into a private deployment directory and replace its illustrative fields. Configure the recipient, chain genesis, native denomination/precision, RPC endpoints, initial finalized block, product, shipping table and policies. The template is **disabled** and has no live merchant defaults. `on-demand` fulfillment has no inventory cap; the quote expires after 30 minutes. Optional `stocked` fulfillment requires a stock count and reserves inventory atomically.
2. Configure operator identity and dispatch/customs/cancellation/privacy policies. An enabled merchant must provide at least one public contact: optional `supportEmail` is a plain email address; optional `supportTelegram` is a bare handle without `@` or a URL, starting with an ASCII letter and containing 5–32 ASCII letters, digits or underscores. Every supplied contact is validated. These fields do not select the private notification destination. Customer contact information remains private; the operator sends acknowledgment and tracking through that contact method.
3. Generate independent encryption and operator tokens securely. Store them in an owner-only `relay.env` outside source control. Select Telegram or SMTP; enabled startup rejects missing notification transport. Never include these secrets or wallet keys in frontend assets. Use mode 0700 for private directories and 0600 for database, backups and environment files. Preserve the database encryption key separately from the database and from the backup key.
4. Set exact HTTPS `allowedOrigins`; do not use wildcards. Bind the relay to loopback behind your TLS proxy, disable request body/header/access logging, and restrict `/v1/operator/` to private operator access. The application also requires a bearer operator token. Enable `SORA_PAY_TRUST_LOOPBACK_PROXY=1` only when the trusted proxy **overwrites** `X-Sora-Pay-Client-IP` with its own `$remote_addr` on every route. The relay accepts that single validated address only from a loopback socket; missing, duplicate/list or malformed headers then fail closed. Default mode ignores forwarding headers and limits the socket peer. A direct health probe in proxy-trust mode must supply `X-Sora-Pay-Client-IP: 127.0.0.1`; do not expose that header as an accepted browser CORS header.
5. Review host capacity, service ownership, private storage permissions, backup retention and incident response before installation. Optional `storageMinimumFreeBytes` is a positive integer byte string for the actual database volume; omission leaves the storage guard unconfigured. Optional `storageResumeFreeBytes` selects a startup and authenticated-reset reserve; it requires `storageMinimumFreeBytes` and must be at least that minimum. Both accept exact byte counts through uint64. If the resume setting is omitted, startup and reset use the configured minimum. A configured guard checks space with integer arithmetic and durably pauses new admission below the ordinary floor or on measurement failure. A saved pause remains closed until reset even after sufficient space returns. If persisting it fails, admission remains closed in memory and persistence is retried; failed writes cannot preserve pause history. Recovery, scanning, notifications and refund work remain independent. Include release and backup allowances in the merchant's capacity procedure. When upgrading from an earlier release, explicitly configure any startup/reset reserve previously supplied by its implicit 10 GiB floor; see the [0.2.5 migration note](../README.md#025).
6. Start with `node --env-file=/private/relay.env dist/relay/cli.js serve`. The relay stays unready during catch-up, RPC failure, denomination/precision mismatch or incomplete setup. `/healthz` reports chain readiness and optional storage admission readiness. Evaluating health/catalog admission may persist a pause. Alert on non-readiness and old undelivered work; no inbound webhook can assert payment.

Configure `chain.rpcUrl` explicitly. If its pruning horizon is shorter than a possible outage, also configure an approved `chain.archiveRpcUrl` exposing historical event state. There is no default archive endpoint. The reader obtains finalized height and canonical block hash from the primary; fallback is used only for unavailable historical state. Archive genesis, block hash and returned header must match the primary identity. An archive cannot extend the primary's finalized height.

Unavailable history raises `archive_required`, preserves the durable cursor and disables new checkout. Never skip the cursor to regain readiness. A brand-new deployment should select a recently verified finalized `startBlock` before accepting orders; an existing database always resumes its saved cursor. Rehearse durable recovery across the primary's pruning horizon before launch.

With `pricing.kind: exact-xor`, set exact `product.priceXor` and shipping `priceXor` strings. They stay fixed until the merchant changes the catalog and advances `pricing.version`. Public pricing metadata contains only `{kind:"exact-xor",version}`; internal fiat audit snapshots and original carrier amounts remain private. Codec conversion uses `10^asset-decimals`; denomination is a consistency guard, not an extra multiplier. Optional `jpy-fixed-usd` pricing requires the merchant's explicit `usdPerXor` and supports launch-fixed or daily provider snapshots. Saved orders never reprice.

Shipping tables define route and quantity/weight eligibility. Optional `approvedShippingCountries` further restricts the available routes; omission leaves the configured table eligible, while `[]` makes every destination inquiry-only. `blockedCountries` adds explicit holds. The catalog intersects those policies with carrier availability, and order creation validates them again. Daily refresh cannot grant approvals, add unpriced bands or change frozen XOR amounts. A carrier/provider failure pauses new checkout while saved orders remain recoverable. Product-specific import, labeling, customs and dispatch requirements belong in the merchant's own fulfillment runbook; carrier availability does not establish them. See [provider interfaces](providers.md).

## Public API

All responses have `Cache-Control: no-store`. JSON request limit: 16 KiB. No query parameters. Bearer secrets and private customer fields must never enter URLs, analytics, error telemetry, public messages or blockchain comments.

| Route | Request and behavior |
| --- | --- |
| `GET /v1/catalog` | Safe merchant, pricing, product, shipping and chain fields. Exact-XOR pricing contains only `{kind:"exact-xor",version}`; no internal fiat audit fields are public. Disabled unconfigured stores return `{enabled:false,version}`. Enabled but currently unready stores return catalog with `enabled:false`. |
| `POST /v1/orders` | `{productId,quantity,shippingRateId,payer,address:{name,line1,line2?,city,region?,postalCode?,country},contact:{type:'email'\|'telegram',value},idempotencyKey}`. Random UUIDv4/32-byte key must be persisted locally before POST; it is a private capability. Validates server catalog, quantity weight, country and payer. Returns `{orderId,recoveryToken,paymentRequest,status,notificationStatus,paymentPending}`. |
| `POST /v1/orders/recover-create` | `{idempotencyKey}` restores a lost create response without retaining or replaying shipping details in the browser. Returns no PII. Same-body create retry is idempotent; a changed body under the same key is rejected. |
| `GET /v1/orders/:id` | `Authorization: Bearer <recoveryToken>` returns private status, receipt, tracking/refund details; no address/contact. |
| `POST /v1/orders/:id/payment-attempt` | Same auth, `{}` body. Atomic one-at-a-time signing lease, returns `attemptToken`. Another tab cannot acquire a second lease. |
| `POST /v1/orders/:id/payment-attempt/cancel` | Same auth, `{attemptToken}`. Release only after explicit wallet rejection before submission; never invoke after an uncertain broadcast. |
| `POST /v1/orders/:id/transaction` | Same auth, `{transactionHash}`. Hint only; does not set paid status. |

Address `name`, `line1`, `city` and two-letter uppercase `country` remain required. `postalCode` is optional: an omitted, empty or spaces-only value is stored as `""`, so checkout can accept addresses without a postal code. A supplied postal code must be a string of at most 200 characters without control characters; `null` and other value types are rejected. All supplied address fields are trimmed and retain the same length/control-character validation. Equivalent omitted/empty postal values produce the same idempotent order. Volunteers still review delivery completeness and destination requirements before shipping.

The front end pins chain/native asset/merchant recipient and separately validates a quote before opening a wallet prompt. Persist the recovery capability in session storage, permit downloading a receipt, and use a URL fragment only if a recovery link is needed. Never attach recovery data to query strings. Payment references are random and public; no customer data belongs in the transfer comment.

## Closing new orders while preserving recovery

The reusable nginx artifacts in [`deploy/nginx`](../deploy/nginx/) close new orders and signing leases while preserving authenticated recovery. They are a separate ingress control from the relay's optional durable storage guard. Installing these templates exposes customer recovery routes and requires a reviewed deployment; a paused map does not make the whole API private. Pin the selected artifacts and verify them against the intended nginx version before installation.

The pilot uses one shared server/guard configuration and swaps only the admission map:

| Artifact | Installation role |
| --- | --- |
| `sora-pay-pilot-http.conf.example` | Include once in nginx's `http` context; supplies the public rate-limit zone and the exact active-map include. |
| `sora-pay-pilot-server.conf.example` | Include only inside the merchant HTTPS server selected for this API. Requires nginx 1.29.3 or newer. |
| `sora-pay-admission-guard.conf` | Install at `/etc/nginx/snippets/sora-pay-admission-guard.conf`; the customer proxy location includes it. |
| `sora-pay-admission-open.map.conf` | Reviewed map bytes for allowing new requests when all launch and storage admission checks pass. |
| `sora-pay-admission-paused.map.conf` | Reviewed map bytes for returning `503` to new order creation and signing-lease requests only. |

Install exactly one selected map at `/etc/nginx/snippets/sora-pay-admission-map.conf`. There is deliberately no optional include, wildcard include or fallback variable initialization: an absent map/file or undefined guard variable must fail `nginx -t`. The [nginx map module](https://nginx.org/en/docs/http/ngx_http_map_module.html) operates in `http` context; these maps use quoted, anchored, case-sensitive regex keys because literal map keys match without case sensitivity. The guard uses only [`return` inside `if`](https://nginx.org/en/docs/http/ngx_http_rewrite_module.html#if).

The keys use `$request_method:$uri`. Nginx's [`$uri`](https://nginx.org/en/docs/http/ngx_http_core_module.html#var_uri) is the normalized path without the query string, and [`proxy_pass` with a URI](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass) replaces the matched `/sora-pay/v1/` prefix with `/v1/` while preserving the endpoint suffix. The shared guard rejects normalized paths containing a backslash with `400` in both modes: Node's URL parser treats backslashes as separators, so forwarding them could bypass nginx's route or operator checks. The relay rejects query parameters independently. Do not replace `$uri` with raw `$request_uri`, use a case-insensitive pattern, broaden the pattern to all `POST`s, remove the ambiguous-path check, or strip the endpoint suffix.

| Public request | Paused behavior |
| --- | --- |
| `POST /sora-pay/v1/orders` | `503` before proxying a new order. |
| `POST /sora-pay/v1/orders/:id/payment-attempt` | `503` before granting a new signing lease; ID shape matches the relay's `[a-f0-9-]{36}` route. |
| `GET /sora-pay/v1/catalog` | Forward unchanged. Browsing remains available. |
| `POST /sora-pay/v1/orders/recover-create` and `GET /sora-pay/v1/orders/:id` | Forward unchanged, retaining private capability/authentication checks. |
| `POST /sora-pay/v1/orders/:id/transaction` and `POST /sora-pay/v1/orders/:id/payment-attempt/cancel` | Forward unchanged for payment recovery or explicit pre-broadcast wallet rejection. |
| `OPTIONS` customer requests | Forward for the relay's exact-origin CORS handling. |
| `/sora-pay/v1/operator` and its descendants | Remain denied publicly with `403`. Use the separately authenticated private operator path. |

The catalog may still report enabled while this ingress pause is active, so an already-open page can display a quote. Saving a new order or acquiring a new lease fails; there is no dedicated low-storage banner. Nginx does not emit or reflect CORS headers itself, so a cross-origin browser may show a generic connection/save error for its `503`. Do not add wildcard or reflected CORS to conceal that limitation.

A pause affects new requests, not leases already issued, wallet prompts already opened, or signed/broadcast transactions. Those payments can still complete. Never cancel an uncertain lease, repeat a transfer, or advance the scan cursor because ingress was paused. Keep the relay, scanner and outbox running and preserve existing recovery and transaction hints. Manual transfers to the public wallet also remain possible and require reconciliation.

Before first installation, run the offline tests and then the isolated real-nginx verifier against the same approved nginx binary/version that serves the host:

```sh
node --test tests/relay/admission-ingress.test.ts tests/relay/admission-recovery.test.ts tests/relay/admission-verifier.test.ts
python3 deploy/check-admission-ingress.py --nginx /absolute/path/to/nginx
```

The verifier uses a temporary prefix, ephemeral loopback listeners and a synthetic upstream; it checks missing-map syntax failure, actual URI routing, open → paused → open reloads, recovery suffixes, operator denial, no-store and proxy-header behavior. It does not use the merchant, real orders, credentials, live nginx configuration or production listeners. It cleans up only its own processes. A no-argument invocation reports its plan without starting a process. Test results establish the checked version/configuration behavior, not a production pause or a completed store launch.

For a reviewed pilot installation, preserve the existing server configuration and verify that unrelated application routes and public operator denial are unchanged. Confirm the Node listener remains loopback-only, trusted-proxy mode is explicitly configured, and nginx overwrites `X-Sora-Pay-Client-IP` with `$remote_addr` while clearing forwarded client-IP headers. Keep access/error request logging disabled, `no-store`, 16 KiB request limits, rate limits, timeouts and disabled proxy cache/retries/buffering intact. The application still owns exact-origin CORS and bearer authentication. Do not expose `/healthz` or an operator route through this customer location.

The customer proxy location explicitly uses [`add_header_inherit on`](https://nginx.org/en/docs/http/ngx_http_headers_module.html#add_header_inherit) with its own `Cache-Control: no-store` header. Standard inheritance lets the nested return-only guards retain that local header on `400` and `503`, while the location's own header definitions replace parent-server headers. Setting this location to `off` also disables inheritance inside the guards and drops `no-store` from their responses. The other five locations retain `add_header_inherit off`. Verify both guard responses and the absence of inherited parent cache/CSP headers in the isolated nginx test.

To pause an installed pilot:

1. Record aggregate free space, relay health, scan cursor, notification backlog and backup status. Confirm the active nginx master command/owner/config path and the reviewed server, guard and current map hashes. Do not inspect or log customer payloads or bearer tokens.
2. Preserve the previous map with its hash and permissions. Stage the reviewed **paused** bytes as a regular temporary file in the same snippets directory, with the same owner/mode, then atomically rename it over the exact active-map path. Change no merchant settings, database, runtime or other service's configuration.
3. Test the complete active nginx configuration with the verified binary and `nginx -t`. If validation fails, restore the prior on-disk map and validate again without reloading. Running workers still use their previously loaded mode, so a failed pause is an unresolved incident; do not report admission closed.
4. Gracefully reload only the verified nginx master through its established service procedure. Confirm reload success and test fresh connections: harmless synthetic invalid create and lease requests must return `503` from nginx; catalog/recovery/hint/cancel paths must still reach the relay; public operator variants must remain `403`. Verify no-store headers and unchanged unrelated application routes. Use synthetic invalid capabilities or controlled fixtures; never create a real order or send a payment as a probe. A reload or probe failure does not prove closure; keep the incident open and check which mode is active.
5. Continue scanner/outbox and backup checks while the responsible service owner restores capacity. Existing workers may finish in-flight requests during reload; reconcile all already-issued leases and submitted transactions. Do not restore an older database, rewind or skip the cursor, or stop reconciliation to simulate a successful pause.

Reopen by the same reviewed map replacement, syntax-check, reload and fresh-connection checks using the **open** map only after the storage admission reserve, reconciliation and current verified backup requirements pass. Check that a synthetic invalid new-order request reaches relay validation rather than nginx `503`; this does not require a real order. When a pause is required, never automatically revert to open merely because the reload/probe failed. The preserved map is configuration recovery evidence, not authorization to resume admission.

## Fulfillment operations

Use a trusted operator client or CLI that passes `Authorization` from the private environment; do not put tokens in shell arguments/history. Requests below require the operator token and VPN access. The shared token authorizes the trusted volunteer team; `owner` is an operational assignment identifier, not a separate authenticated security principal.

- `POST /v1/operator/admission/reset` with `{}` clears only the configured durable storage pause after sufficient space is verified; extra body fields return `400`, reset failure returns `503`, and unconfigured deployments return `404`. Review the capacity budget, scanner reconciliation and current backup first. This does not open public ingress, enable a merchant or clear uncertain payment/refund leases. `ready` on private health remains chain readiness; optional `admissionReady` and catalog `enabled` also include the storage gate.

- `GET /v1/operator/orders` returns up to 500 private orders, prioritizing outstanding paid/review/refund work oldest first with address/contact, ownership, received/refunded exact amounts and receipt evidence. No public admin page is exposed.
- `POST /v1/operator/orders/:id/claim` with `{owner}` assigns once. Another owner gets conflict.
- `POST /v1/operator/orders/:id/approve` with `{owner}` approves a late exact payment after volunteer review and stock availability, when applicable. Wrong/extra amounts require reconciliation/refund, never automatic shipment.
- `POST /v1/operator/orders/:id/ship` with `{owner,tracking,shippingReviewed:true}` requires paid, assigned state and a fresh legality/carrier review. It queues a private volunteer status notification; the volunteer sends tracking to the customer's contact. Repeated shipments are rejected.
- `GET /v1/operator/orders/:id` retrieves a specific private order, including older completed orders outside the queue limit.
- `GET /v1/operator/orders/:id/evidence` returns encrypted-at-rest finalized incoming/outgoing transfer evidence for reconciliation. A mismatched incoming amount never appears as a valid original-quote customer receipt.
- `POST /v1/operator/orders/:id/refund` with `{owner}` reserves the outstanding refund, verified original payer and a fresh public reference. A net-policy draft has no signable `amountCodec` until the relay obtains a trusted fee quote. Repeating the request preserves the obligation. Before signing, acquire `POST /v1/operator/orders/:id/refund-attempt` with `{owner}` and persist its `attemptToken`; the relay rechecks the fee before granting the lease. Another attempt is rejected while the lease is unresolved. Report a broadcast with `refund-transaction` using `{owner,attemptToken,transactionHash}`. Use `refund-cancel` with `{owner,attemptToken}` only after explicit wallet rejection before broadcast; uncertain or submitted attempts stay locked for reconciliation. A volunteer signs only the quoted native-XOR `liquidityProxy.xorlessTransfer`, from the merchant wallet, for the exact net `amountCodec` and public reference. No API can simply mark a refund successful. See the accounting rules below.
- `POST /v1/operator/orders/:id/refund-reconcile` binds an already-finalized, direct native-XOR `assets.transfer` to one pending refund when that wallet transfer omitted the public reference. The exact body is `{owner,attemptToken,expectedReference,expectedGrossAmountCodec,expectedAmountCodec,blockNumber,blockHash,transactionHash,eventIndex}`. Amounts and block number are canonical integer strings; event index is a nonnegative integer. The existing assigned owner, signing lease and exact pending gross/net/reference must match. The request accepts a locator, never caller-provided evidence or a replacement reference. An existing transaction hint must agree with the located transaction. Do not create a retrospective lease to fit an old transfer.
- `POST /v1/operator/orders/:id/refund-agreed-deduction` records explicit customer consent for one fixed deduction from an existing unsigned version-1/full refund. The exact body is `{owner,expectedReference,expectedGrossAmountCodec,agreedDeductionCodec,consentId,consentNote}`: canonical positive codec strings, a UUIDv4 consent ID, and a private note recording the actual instruction. The assigned operator must establish consent before using this route; the API records that attestation, not a customer signature. The transaction compares owner, reference, gross and outstanding liability, rejects a prior amendment or any signing history (including a canceled attempt), and requires a pending full refund with no quote or receipt. Identical consent retries are read-only; competing or changed consent returns `409`. This operation does not sign or broadcast. It queues one `refund_amended` volunteer alert, with agreed and actual fee amounts clearly separated.

Set `reviewEveryPaidOrder:true` when every paid order needs operator review and the `approve` operation before shipment. Payment mismatch, expiry, additional payment, or unavailable stock enters `shipping_review` instead of enabling shipment. Multiple distinct finalized transfers with the same reference accumulate the amount owed; replaying the same event is ignored. Payment acceptance and notification insertion are one SQLite transaction. Notifications are at least once: network ambiguity may duplicate a message, so volunteers use the stable order ID and private assignment queue, not the number of messages, to decide fulfillment. Delivery failures persist with bounded exponential retry. Atomic 60-second outbox leases prevent concurrent workers from sending one job together; only the current lease owner can acknowledge it. External delivery remains at least once after a crash or uncertain remote acknowledgment. Do not accept new payments on an unready service. A relay restart rescans from the durable next-block cursor and can recover a transfer even if its browser closed without sending a hash.

## Refund accounting

`refundPolicy` is an explicit versioned setting: `{ "version": 1, "mode": "full" }` returns the full outstanding XOR and the store pays the outbound fee; `{ "version": 2, "mode": "net-network-fee" }` deducts the verified outbound SORA fee, capped at the quote. Choose the policy in merchant configuration before accepting orders. A missing setting defaults to version 1. Orders snapshot the policy when created, and missing historical snapshots always mean version 1. Changing merchant configuration never changes a saved order or an existing pending refund. Do not rewrite historical terms as part of a deployment.

The original payment fee never enters `receivedCodec` and is not deducted again. Refunds expose `grossAmountCodec`, a quoted net `amountCodec`, and `feeQuote` containing exact fee, finalized quote block and expiry. The quote is for one direct native-XOR transfer with the public reference, zero tip and no batch or proxy fee allocation. The relay serializes a dummy-signed envelope solely to query the finalized RPC fee; no spending key is held or transaction submitted. Envelope size, nonce or runtime changes can alter the eventual fee. A changed quote is reviewed before signing; an acquired or uncertain signing lease freezes it.

Only the trusted finalized reader can supply `receipt.evidence.networkFee`. For the current runtime it corroborates one same-extrinsic `xorFee.FeeWithdrawn` with `transactionPayment.TransactionFeePaid`, checks the actual native fee payer and zero tip, and does not sum these two reports of the same fee. Nested, missing or ambiguous fee evidence is not charged to the customer. Generic receipt matching verifies the transfer; fee authority comes from the trusted reader, never an operator or browser assertion.

After the exact outgoing transfer finalizes, `refundedCodec` increases only by XOR actually returned. `refundFeesCodec` increases by the smaller of the verified actual fee and quoted fee. The store absorbs a higher actual fee. A lower actual fee leaves `feeCorrectionCodec` on that transfer and `refundFeeCorrectionCodec` on the order; it remains owed and is returned first as a separate `feeExempt` transfer whose network fee the store pays. Missing authoritative fee evidence causes a zero deduction and the entire quoted fee becomes a fee-exempt correction; the observed transfer is retained and never blindly repeated. A later additional customer payment is handled separately, after that correction. The `refund` object always describes the latest transfer, not a lifetime aggregate.

An order is fully refunded only when received XOR minus XOR returned, verified deducted fees, finalized agreed deductions and fulfilled purchases is zero. Insufficient gross funds for a positive net transfer leave a reviewable obligation; never create a zero-value transfer, erase the liability or mark it refunded. Keep enough XOR for existing liabilities, legacy full refunds, fee-estimate differences and fee-exempt corrections. The customer pays no extra fee for correcting the store’s estimate. Refunds have no fixed processing deadline; volunteers provide updates through the chosen contact method.

An explicitly agreed fixed deduction is separate from network-fee accounting. The original order policy never changes. An encrypted `refundAmendment` preserves the operator, consent note, exact prior obligation, original policy and server timestamp; only authenticated operator detail exposes it. Customer receipts expose `refund.agreedDeduction:{version:1,amountCodec,consentId,recordedAt}` alongside the original policy and exact gross/net amounts. The same public refund reference and verified paying wallet are retained. Only one such amendment is allowed per order; later additional payments retain their original full-refund terms.

An amended obligation remains `feeExempt:true` because its agreed deduction is separate from network-fee accounting. It has no `feeQuote`; fee estimation must not reprice the agreed net. The signing wallet must still check actual fee and available balance before submitting the exact transfer. Any actual fee is paid by the merchant and reported only from trusted finalized evidence.

An amendment does not settle money before finality. On the exact finalized outgoing transfer, `refundedCodec` increases by the actual return and `refundAgreedDeductionsCodec` by the agreed amount, once. The final liability calculation also subtracts this separately recorded agreed deduction. `deductedFeeCodec` and `feeCorrectionCodec` are zero for that transfer; `actualFeeCodec` is optional independent evidence. A lower, higher or unavailable actual fee never changes the agreed deduction or creates an automatic correction that reverses the customer's instruction. Normal version-2 fee deduction and correction rules remain unchanged. Customer views and Telegram/email volunteer alerts distinguish pending from finalized returns, agreed deduction from actual fee, and original policy from this one consent.

## Manual reconciliation of an already-sent refund

The reconciliation route rereads the selected block and event through the trusted chain reader. The primary RPC supplies finalized height and the canonical block hash; approved archive fallback must match that identity. It accepts only a direct signed `assets.transfer` whose signer, three arguments, single `assets.Transfer`, and corresponding single `balances.Transfer` all agree on native XOR, payer, recipient and exact amount. Failed/nested/batched/ambiguous transfers and the balances mirror as a separate locator are rejected. The transfer timestamp cannot precede the original finalized payment or the refund's recorded signing start. A transfer with no known existing signing lease needs separate investigation; this operation does not fabricate signing history.

Automatic reference matching is unchanged. A manually bound customer receipt retains the original expected refund reference in `receipt.request.reference`, the actual absence of an on-chain reference in `receipt.evidence.reference:null`, and `transferKind:'assets-transfer'`. It includes `reconciliation:{version:1,kind:'operator-bound',expectedReference,recordedAt}`. Use core `verifyFinalizedRefund(expectedRequest, receipt)` to validate either an ordinary strict receipt or this explicit manual variant; `verifyFinalizedPayment` continues to reject the missing reference. The original incoming payment receipt, saved order policy and refund reference remain intact.

The transaction atomically saves a private operator/lease-digest/CAS audit, consumes the physical transfer once, settles through the existing refund accounting, and queues the normal finalized notification. An assets event and its balances mirror cannot produce two refunds; a transaction already consumed elsewhere is refused. Exact retries return the same recorded result without another RPC read, accounting change or notification. Altered bindings are rejected. No scanner cursor moves, historical evidence rewrites, database edits or repeat transfer are part of reconciliation. A failure or uncertain response requires a private status/evidence reread before retrying the same request.

An explicitly agreed deduction settles separately from the actual network fee: the returned XOR plus that finalized deduction resolves the corresponding gross obligation once. Direct-transfer fee proof uses one matching `xorFee.FeeWithdrawn` and `transactionPayment.TransactionFeePaid` with zero tip; these describe one fee and are not summed. Missing or ambiguous fee evidence remains absent. Normal full-refund and net-fee accounting remain unchanged.

## Retention and backup recovery

The service encrypts PII with AES-256-GCM using per-record random nonces and record ID authenticated data. Address/contact are redacted after 30 days following shipment/refund by default and 24 hours after an unpaid quote expires. The original payment address, exact amounts, receipts and event identities remain for payment reconciliation. A late payment after address redaction needs the customer to contact support privately. Backups and private notification inboxes contain copies: configure matching retention in the backup destination, Telegram group and email inbox. Where legal accounting retention requires longer storage, adopt an explicit operator retention policy and restricted storage rather than silently retaining addresses forever.

Create an encrypted backup with `node --env-file=/private/relay.env dist/relay/cli.js backup`, using a unique `SORA_PAY_BACKUP_PATH` and a separate `SORA_PAY_BACKUP_KEY`. SQLite's backup API takes a consistent snapshot; the complete result is encrypted. The temporary snapshot directory is private and removed. Existing backup destinations are never overwritten. Copy encrypted backups only to an explicitly approved private destination; never IPFS or public repositories.

The current source loads only local backup dependencies for `restore`, and loads RPC, HTTP, catalog and notification modules only for `serve`. Operator wrappers should give restore and database verification separate bounded timeouts and retain safe phase/duration records. Never log subprocess commands, environment values or raw output from a failed private restore. A verification timeout leaves the encrypted archive unverified; it must not replace the last verified backup or trigger retention pruning.

For recovery, stop the exact relay service, preserve its current database/WAL, and use the `restore` command to a **new** database path. Supply the original database encryption key and separate backup key; an incorrect database key fails on startup. The database pins its original chain genesis and merchant wallet; it refuses startup under a different merchant identity. Point the private env at the restored path, start one relay instance, let it rescan finalized blocks from its saved cursor, inspect order/outbox counts, and rehearse a recovered receipt lookup. Never run two notification workers against the same database. Backup restore may resend previously delivered messages; use order IDs and queue assignments to prevent duplicate shipments. Rehearse restore before accepting real payments.

No live deployment, purchase, notification or refund is performed by the test suite. Before accepting customer payments, complete an end-to-end payment/refund rehearsal, configure private notification delivery, verify recovery, and follow the merchant's deployment and fulfillment procedures.

## Local customer checkout rehearsal

`deploy/rehearsal-proxy.mjs` provides a customer-only browser route over a **manually established SSH forward**. It runs only when explicitly invoked and loads no relay environment, operator token, wallet key or SSH credential. Build first with Node 26 and the locked Yarn setup from the README. The command without flags prints usage and exits.

Before any enabled rehearsal, block public customer ingress at the approved nginx host and verify that block externally. A null frontend `relayUrl` and CORS do not prevent direct API access. Keep the published frontend configuration unchanged. Enable the private merchant only after notification credentials, backup bindings and the reviewed start block are ready; this local proxy neither changes nor bypasses those launch gates.

Open a separate terminal and establish the SSH forward using the relay host's verified host key and operator authentication. Substitute your own account and host; do not put credentials in the command or disable host-key checks:

```sh
ssh -NT -o ExitOnForwardFailure=yes -o StrictHostKeyChecking=yes \
  -L 127.0.0.1:39850:127.0.0.1:39848 operator@relay.example.test
```

Then run the local proxy from this repository:

```sh
node deploy/rehearsal-proxy.mjs \
  --listen-port 39849 \
  --upstream http://127.0.0.1:39850 \
  --frontend-origin http://127.0.0.1:41829 \
  --upstream-origin https://shop.example.test
```

All four flags are mandatory. The upstream and frontend origins must use literal `http://127.0.0.1:<port>` with distinct non-default ports; credentials, paths, queries, aliases and non-loopback addresses are rejected. `--upstream-origin` is the merchant's exact HTTPS origin accepted by the relay. No environment variable changes these endpoints.

Serve the integrating frontend at the exact configured local origin and point only that local development session at `http://127.0.0.1:39849`. Use the same chain and merchant request validation as the deployed application. Keep published configuration unchanged. The proxy binds only to loopback and checks Host, Origin and peer; missing or `null` origins are rejected. A browser on another device cannot use this desktop loopback address, so supported mobile-wallet signing requires a separate rehearsal setup.

The proxy allows only `GET /v1/catalog`, `POST /v1/orders`, `POST /v1/orders/recover-create`, `GET /v1/orders/:uuid`, and customer `transaction`, `payment-attempt` and `payment-attempt/cancel` POST routes. It denies operator/health routes, other methods, query strings, arbitrary URLs, encoded path variants, CONNECT and WebSocket upgrades. Preflight permits only the selected route's method plus Content-Type and Authorization. Recovery authorization is forwarded only for customer order routes and must be the existing 64-hex recovery capability; never enter an operator token in the frontend.

Upstream requests go solely to the fixed SSH forward, with the configured merchant Origin and overwritten `X-Sora-Pay-Client-IP: 127.0.0.1` for the relay's explicitly configured proxy-trust mode. Incoming cookies, forwarding headers and arbitrary headers are discarded. Upstream cookies, redirects and CORS headers are never passed through. Responses use the exact local browser origin and `Cache-Control: no-store`. There are no request URL/header/body logs, retries or persisted proxy records. POST JSON is limited to 16 KiB; each body/upstream wait has a 15-second deadline and upstream JSON is capped at 1 MiB.

Stopping the proxy with Ctrl-C closes its listener and drains for at most five seconds; stop the separately launched SSH forward as well. A timeout or browser closure may occur after an order or payment attempt reached the relay: use the existing saved idempotency key/receipt recovery and payment-status flow, never assume failure authorizes another transfer. Keep the public ingress block until the internal purchase/notification/fulfillment/refund rehearsal and launch review pass. Operator access remains a separate authenticated private workflow and is never available through this customer proxy.
